# TileLang Debugger

面向 NVIDIA H200 的 TileLang 调试工具。当前处于设计阶段，尚未实现工具接口或完成设备验证。

用户在原始源码中选择观察位置、循环迭代和 block，工具自动插入 monitor，复用 TileLang 的打印及编译机制采集运行期信息，并将结果关联回源码。

## 当前范围

- 目标设备：NVIDIA H200。
- 源码选点和自动插桩；第一版优先支持普通语句、循环及常见 tile 操作。
- tile 输入、输出和访问信息的定点观察。
- 用户提供 reference，工具负责对齐和比较。
- 原始程序与插桩程序的 IR 导出、运行记录和结构化报告。
- 为合作方提供硬件适配接口；其他硬件的具体实现由合作方负责。

这里列出的是拟开发能力，不代表已支持。

## 使用流程

```text
选择原始文件、源码行和操作
    → 选择循环迭代、block、采集对象和等级
    → 自动插入带观察点 ID 的 monitor
    → TileLang 编译并在 H200 上运行
    → 解析采集记录，可选地与 reference 比较
    → 按原始源码位置展示结果及关联 IR
```

源码定位拟使用 Python AST。插桩前保存原始位置，为每个观察点分配 ID；日志通过该 ID 回到源码，不从 CUDA 文本反推位置。同一行多个操作需要进一步选择。宏内部、动态生成源码及其他复杂形式的支持范围待验证。

循环选择采用原始循环的迭代序号，并明确从第 1 次开始计数。嵌套循环分别指定各层次数；迭代序号与循环变量取值分开保存。循环展开及软件流水化后的采集对应关系需要验证。

## IR 导出

保留两种明确区分的编译产物：

| 产物 | 用途 |
|---|---|
| 未插 monitor 的原始程序 IR | 检查原始逻辑与布局，作为比较基线 |
| 插入 monitor 后的程序 IR | 解释本次采集实际执行的程序，包括新增搬运、存储和同步 |

对比相同编译阶段时，应使用相同输入特化、目标和编译选项，分别编译原始程序与插桩程序。不能从插桩后的 IR 删除打印语句来冒充原始编译结果，因为 monitor 可能影响布局、流水和同步。

计划按需保存前端 IR、关键 lowering 阶段 IR 及生成的 CUDA。每份产物记录是否插桩、编译阶段、源码摘要和编译配置；运行记录关联实际执行的插桩产物。

## 数值观察与 reference

- reference 由用户提供，不自动为任意程序生成参考实现。
- 最终输出可与完整参考实现比较；中间 tile 必须与同一观察点、block 和迭代对应的参考数据比较。
- 支持误差统计、超差元素位置，以及 NaN/Inf 的独立统计。
- 类型转换问题通过配对采集转换前后的值观察。
- 数值敏感操作通过观察输入和结果辅助定位，例如接近零的除数或负数开方。
- 多观察点可展示异常在已采集位置间的变化，不将最早观测到的异常直接认定为根因。

现有文本打印可用于原型。用于精度比较时，需要保证足够的数值保真度，并识别记录丢失或截断；浮点输出格式及必要的原值编码尚待设计。

## 访问观察

第一版区分源码层的逻辑访问与编译后的实际访问。

以 `T.copy(A[bi * BM, k * BK], A_shared)` 为例，源码层 monitor 可记录：

- 观察点 ID、block、循环迭代和相关标量取值；
- 源与目标 buffer 的 shape、dtype 和可获取的 stride；
- 本次源起始索引 `(bi * BM, k * BK)`、目标范围及 tile extent；
- 源码中显式给出的访问条件。

范围由所选操作的 buffer region 语义确定，不能只根据起始索引猜测长度。简单 copy 可通过操作参数解析；无法可靠解释的表达式应明确标为不支持或未知。

对于连续矩形访问，可检查每一维的半开区间 `[start, start + extent)` 与 buffer 边界的关系。越过逻辑边界仅表示需要进一步检查：边界 tile 可能被编译器正确掩码或填充，不能直接报告为非法访问。

编译器生成的掩码、线程到元素的布局映射、向量化和物理访存方式应从相应阶段 IR 获取。源码层 monitor 本身不能完整提供这些信息。若需要精确的运行期有效掩码或逐线程物理访问记录，需要在相应 lowering 阶段增加采集，属于后续扩展。

访问观察优先记录索引计算和元信息，不为打印地址内容额外执行可疑的内存读取。对间接索引、scatter/gather 等场景，需要专门处理，不能以简单矩形范围替代。

## 同步与执行语义

原型复用 TileLang 的 `T.print`。在已检查的源码中，fragment 打印通过 shared memory 中转，后续 ThreadSync 根据读写依赖插入 barrier；普通 `T.gemm` 的 Hopper WGMMA 路径包含完成等待。

具体行为随 TileLang 版本、操作和编译选项而变。需锁定版本，用生成 IR/CUDA 及 H200 测试验证。显式异步操作必须另外核对完成等待，不能将 shared-memory barrier 视为任意异步操作的完成保证。

monitor 可能改变资源占用、同步和流水行为，运行记录应注明插桩配置。

## 采集等级与分层

两者分别设计：

- 采集等级：摘要、完整值。
- 分层流程：按 block / 迭代查看摘要，再选定 tile 展开元素、索引及 reference 差异。

若详细采集通过重跑实现，需要记录输入、随机状态及运行身份，不把不同运行的记录当作同一次执行。具体交互与验证标准待确定。

## 开发顺序

1. 源码选点、条件打印、观察点 ID、日志解析和两种 IR 导出。
2. reference 接入、数值保真、误差统计及多观察点比较。
3. 访问观察、分层采集、结构化报告和硬件适配接口。

验证案例应包含正常对照与故障案例，覆盖数值偏差、NaN/Inf、类型转换、敏感操作和异常访问；同时验证条件过滤、同步、记录完整性及源码映射。
